# Support Ticket Analysis Dashboard — Build Prompt

You are building one self-contained, offline-capable HTML file analyzing AI-platform support tickets handled since January 2026. This is for a manager-facing presentation — every number on the page must be computed directly from the source CSVs below, never invented, templated, or padded.

## Non-Negotiable Data Rules

These rules come before any page spec below — violating any one of them produced the discrepancies in the last build attempt, and they must not repeat.

1. Discover before coding. Load each CSV first and print its real column names, dtypes, row count, and 3–5 sample rows. Map every field this prompt needs (ticket ID, title, assignee, status, every stage-transition timestamp, original tag, assigned meta-tag, assigned subtag) to whatever the actual headers turn out to be — never assume a column name from this prompt is the literal header.
2. Force the ID column to one type. The ticket ID has previously been read as text in one file and numeric in another, which silently broke duplicate detection. Cast every ID to a stripped string (strip whitespace, strip a trailing ".0" left over from numeric parsing) before any comparison, join, or dedup step.
3. Deduplicate before combining. Any "Overall" or "Whole_Data" view must be deduplicated by the normalized ID first. Log how many duplicate rows were found and removed for each combination — this count must be visible in your build notes, not silent.
4. Validate status literals before using them. The On Hold / Cancelled breakdown depends on the exact strings "On Hold" and "Cancelled" existing in the status column. Print every distinct value in that column first. If the exact strings aren't present (casing, spacing, "On-Hold", "Canceled"), do not render an empty or zero-value chart — use the closest actual match and flag the substitution in your build notes.
5. No templated findings. Every sentence in the Key Findings & Actions table must be generated by substituting that dataset's real computed numbers and real tag names into the sentence. Never repeat the same boilerplate sentence across rows.
6. No invented rows. Every row in every table must trace to a real ticket ID in the source data. Never pad a table to reach a round number.
7. One fixed "measurable ticket" definition, used everywhere. A ticket is measurable only if it has both a non-null Created timestamp and a non-null Under Review timestamp. Apply this exact definition to every "measurable" stat on the dashboard — never redefine it per chart or per page.

### Time segments
Report mean, median, and ticket count every time a segment is shown. Each segment is computed only for tickets where both its own endpoints exist — a ticket missing one segment's end date is excluded from that segment alone, not from the others.

| # | Segment | From | To |
| --- | --- | --- | --- |
| 1 | Created → In Analysis | Created | In Analysis |
| 2 | In Analysis → Under Review | In Analysis | Under Review |
| 3 | Created → Under Review | Created | Under Review |
| 4 | Under Review → Close/Done | Under Review | Closed if present, else Done; if both exist use Closed and log the overlap count |
| 5 | Created → Close/Done | Created | Same Closed/Done rule as Segment 4 |

## Navigation, Interactivity & Technical Constraints

- Top nav bar with three tabs: Home, Tagging, Time Bottleneck Analysis. The active tab is visually distinct from the other two.
- The tag click-through is shared and identical across all three pages — the same panel, the same data shape, regardless of which page the click came from.
- Single HTML file. Pure client-side JavaScript. No server or backend. Must open correctly from a local file:// path in a standard browser with no network connection needed after the file is generated.
- Every computed number is embedded as a static JSON object inside the HTML at build time — the page must never re-read the CSVs at load time, so it keeps working even if the source files are later moved or deleted.
- Clean, manager-presentable styling: consistent spacing, readable table headers, legible on a standard laptop screen, no leftover dev placeholders or lorem ipsum.

## Build Process

Run these steps in order:

1. Discover — load all 3 CSVs, print schema, dtypes, row counts, and sample rows. Confirm the field mapping and run the status-literal check from Rule 4.
2. Clean — normalize the ID column's dtype, parse every date column, deduplicate per the view definitions above.
3. Compute — build every metric specified in Pages 1–3 into a single JSON object.
4. Self-check — before rendering, verify: the sum of the 3 raw file counts equals the Home page's "Total raw tickets" tile; Unique tickets ≤ Total raw tickets; each tag's subtag ticket counts sum to that tag's own total. Print this QA summary in your build notes before continuing.
5. Render — generate the single static HTML file with the computed JSON embedded inline.
6. Save — write the file to the output folder specified above.
